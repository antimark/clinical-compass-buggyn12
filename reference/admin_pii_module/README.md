# Clinical Compass — optional clinic-administrator identity access

Рабочий изолированный модуль для `CLINIC_ADMIN`, **не заменяющий** весь Clinical Compass. Написан под Python 3.11+, Flask, SQLAlchemy 2.x, Alembic и SQLite. В архив включены минимальные core-сущности для локального запуска; в реальном проекте их нужно сопоставить с уже существующими моделями. Это не готовая интеграция в чужой репозиторий.

## Состав

- `clinical_compass/models.py`: SQLAlchemy core-таблицы-примеры, отдельные optional ACL-таблицы, feature flags, оргчленства, локальные patient refs.
- `clinical_compass/service.py`: единая проверка полномочий и проекция идентификационных данных для `detail/list/search/sort/export/notification/appointments`.
- `clinical_compass/api.py`: Flask Blueprint `/api/v1`, сессии, CSRF, серверная проверка, JSON API.
- `clinical_compass/security.py`: `scrypt` для паролей, `Fernet` для сохранения значений персональных полей.
- `migrations/`: воспроизводимая Alembic-миграция, включая SQLite-триггеры неизменности шаблонов.
- `scripts/demo_seed.py`: **только синтетические** объекты (разрешён запуск исключительно с `APP_ENV=development`).
- `tests/`: проверки изоляции организаций, двух флагов, разграничения отдельных пациентов, исключений, экспорта, поиска, уведомлений, записи к врачу и удаления optional-таблиц.
- `openapi.yaml`: API-контракт.

## Запуск на своей машине

```bash
cd clinical_compass_admin_access
python -m venv .venv
# Linux/Mac: source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
cp .env.example .env  # на Windows можно скопировать файл вручную
```

В `.env` заменить `SESSION_SECRET` и `PII_ENCRYPTION_KEY` на самостоятельно сгенерированные значения:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Ключ Fernet нельзя хранить в SQLite, исходном коде или Git. Потребуется резервная копия ключа, иначе расшифровать старые данные невозможно. Тестовый/демонстрационный пароль запрещён для реального внедрения.

```bash
mkdir -p data
alembic upgrade head
python -m scripts.demo_seed
python run.py
```

В demo-сееде: пользователи `platform_demo`, `admin_demo`, `doctor_demo`, `patient_alice_demo`, `patient_bob_demo`. **Только для локального синтетического демо:** пароль `DemoPassword!123456`. Все feature flags первоначально выключены.

### Пример работы через API

1. `GET /api/v1/auth/csrf` — получить `csrf_token`, сохранить session cookie.
2. `POST /api/v1/auth/login` с заголовком `X-CSRF-Token`, JSON `{"username":"platform_demo","password":"DemoPassword!123456"}`. Сохранить новый `csrf_token`, возвращённый после авторизации.
3. `PATCH /api/v1/admin/features/clinic-admin-pii` с JSON `{"enabled":true}` — включить глобальный флаг.
4. Повторить PATCH с `{"organization_id":1,"enabled":true}` — включить флаг конкретной клиники (использовать её фактический ID из demo-сееда).
5. Войти как `admin_demo` и вызвать `GET /api/v1/clinics/1/patients` — увидите только разрешённые конкретному пациенту поля и локальные `patient_ref`.
6. Для отключения любого уровня отправить `{"enabled":false}` с соответствующим `organization_id` или без него; новые чтения после commit немедленно возвращают `fields: {}`.

Запросы, изменяющие состояние, всегда требуют cookie и **актуальный** `X-CSRF-Token`, возвращённый после логина; идентичность не берётся из HTTP-заголовка с user ID. При работе с Flask-интерфейсом cookie должен передаваться в том же доверенном origin.

### Управление правами

- `PLATFORM_ADMIN` создаёт версионированные шаблоны; одни и те же `template_key` могут иметь разные `version`, но уже созданные версии не расширяются через API.
- Пациент видит предложенные шаблоны конкретной клинической связи (`GET /me/clinic-links/{id}/pii-templates`) и **сам** применяет конкретную версию (`PUT /me/clinic-links/{id}/pii-policy`, `confirmed:true`).
- Пациент может применить `ALLOW`/`DENY`/`REMOVE` к зарегистрированным identity/contact полям с необязательным сроком истечения.
- При выборе новой версии существующие overrides удаляются, поэтому прежние дополнения не переносятся автоматически.
- `DELETE /me/clinic-links/{id}/pii-policy` отзывает все права в этой клинической связи.
- В любом API, предназначенном для CLINIC_ADMIN, не существует права на `CLINICAL` и `OTHER` fields; свободный текст пациента и клинические таблицы не сериализуются.

**Правило вычисления:** active user ∧ active membership CLINIC_ADMIN в clinic ∧ active organization ∧ active patient–clinic link ∧ global flag ∧ clinic flag ∧ active accepted policy ∧ eligible field ∧ (template READ ∪ unexpired patient ALLOW) ∖ unexpired patient DENY. При отсутствии любого обязательного условия идентифицирующее поле запрещено.

**Не путать:** разрешение видеть локальный `patient_ref` для организации записи не означает разрешение на ФИО и тем более на медкарту. Локальный `patient_ref` генерируется отдельно для каждой клиники и не является платформенным patient ID.

### Поля, фильтры и экспорт

`GET /api/v1/clinics/{clinic_id}/patients?filter_field=first_name&filter_value=Ali&sort_field=first_name&limit=50&offset=0` проверяет права по **каждому пациенту до применения фильтра и сортировки**. Запретная величина не участвует в отборе и не может быть использована для слепого поиска. Для одних пациентов ФИО отображается, для других нет — в одном запросе.

`GET /api/v1/clinics/{clinic_id}/patients/export?fields=first_name,phone&limit=500&offset=0` экспортирует JSON, без raw SQL или произвольного клинического payload. Для каждой записи разрешена только собственная проекция. Максимум 500 записей на запрос; для полного экспорта требуется пагинация.

Административные уведомления содержат только белый список событий записи на приём, `patient_ref` и разрешённые поля; клинические alert-события намеренно не отправляются этим API. Приём связывается с уже существующими активными отношениями пациента с врачом в выбранной клинике, свободная причина визита не принимается.

## Проверка

```bash
python -m pytest -q
alembic check
```

Команды `alembic upgrade head` и `alembic check` проверены на SQLite. Сервисные тесты можно запускать без Flask; Flask-интеграционные тесты запускаются при наличии зависимости. Не использовать SQLite unit tests как замену нагрузочным и concurrency-тестам.

## Встраивание в основной Clinical Compass

1. Не переносить демонстрационные `User`, `Patient`, `ClinicalRecord`, `Organization`, `PatientClinicLink`, `DoctorPatientLink`, `FieldDefinition`, `PatientFieldValue` как дубликаты. Сопоставить внешние ключи с **имеющимся** ядром.
2. Добавить только `AdminPiiTemplate`, `AdminPiiTemplateRule`, `AdminPiiPolicy`, `AdminPiiOverride` и запись в универсальной таблице `FeatureFlag` с кодом `clinic_admin_identifying_data`. Если в ядре есть универсальные feature flags — использовать их вместо демонстрационного класса.
3. Включить `Blueprint` без расширения обязательных колонок `User`/`CLINIC_ADMIN` и без добавления отношений, без которых ORM ядра не запускается.
4. Подставить в `service.py` существующие схемы ролей, согласий, связей и авторизации. В уже работающем приложении не создавать второй параллельный login/session-механизм — перенаправить `actor_id()` на настоящий auth service.
5. Принимать шаблон на фактически существующей связи пациента с клиникой. Не создавать параллельную связь врач–пациент ради работы модульного ACL.
6. **Все** текущие административные маршруты платформы, JSON schemas, Flask views, фоновые задания, уведомления, кеши, файлы, поиск и сторонние интеграции должны использовать проекции `patient_view`/`patient_list` либо их общий сервисный контракт. Одного нового Blueprint недостаточно для гарантии отсутствия утечек из других маршрутов.
7. Для данных пациентов установить единую политику шифрования, ротации ключей, аудита и бэкапов; не создавать второй набор значений или криптографических ключей в production.
8. Миграцию для уже существующей БД **переписать как additive-only**, создающую только опциональные таблицы/флаги; начальная миграция архива создаёт также демонстрационное core-ядро и не должна исполняться поверх настоящей БД без адаптации.

## Полное отключение и удаление

**Временное отключение:** выключить глобальный или организационный флаг. Политики, шаблоны и индивидуальные исключения остаются в БД, но не открывают идентифицирующие поля.

**Удаление в интегрированном проекте:** (а) отключить глобальный флаг, (б) удалить обращения к optional Blueprint/ACL, (в) выполнить заранее проверенную migration, удаляющую `admin_pii_overrides`, `admin_pii_policies`, `admin_pii_template_rules`, `admin_pii_templates` в указанном порядке и только записи `feature_flags` с ключом `clinic_admin_identifying_data`. Не удалять `patient_clinic_links`, `patient_doctor_links`, `patients`, `clinical_records`, `patient_field_values` или другие права платформы. Сначала сделать backup и проверить восстановление на staging. SQLite требует эксклюзивного окна для такого schema change.

## Ограничения и security review до реального использования

- **Это демо-реализация одного ACL-модуля, а не сертифицированная медицинская платформа.** Не загружать реальные персональные или медицинские данные без интеграционного аудита и организационно-правовой оценки.
- Проверка в сервисе является актуальной на момент SQL-чтения; отзыв гарантирует отказ для **последующих** запросов после commit. Уже начатую передачу ответа, ранее выгруженный файл или локальную копию пользователя отозвать автоматически нельзя. `Cache-Control: no-store` ограничивает только стандартное HTTP-кеширование.
- SQLite-перебор пациентов до поиска/сортировки для ясной security-семантики имеет O(N) декодирований и подходит лишь для MVP. Production требует SQL-алгоритма с гарантированной предфильтрацией, авторизованными индексами/токенами и замерами.
- Поиск по расшифрованным полям выполняется **только после ACL**, но при большом количестве пациентов может быть дорог. Нельзя добавлять глобальные plaintext индексы или хеши без отдельного threat modeling.
- Для более жёсткой tenant isolation и многопроцессного отключения flag нужно предусмотреть поведенческие тесты конкуренции и проверку ACL непосредственно перед финальным формированием ответа.
- Отдельные поля зашифрованы Fernet, но метаданные/связи в SQLite не шифруются. Администратор ОС, владеющий ключами и процессом, технически может обойти API-проверки; SQLite не обеспечивает row-level security.
- Записи в `ClinicalRecord` специально не получают endpoints в административном модуле. Остальные существующие клинические API должны обеспечивать собственную авторизацию.
- Триггеры защищают версионированные шаблоны в SQLite; для PostgreSQL надо реализовать эквивалентную защиту и повторить security-тесты.
- В этом демо-сценарии `accepted_at` — техническая фиксация подтверждения, а не юридическое доказательство отдельного согласия. Правовое основание, тексты согласий и их версии интегрируются с общим `consent` модулем.
- Для production отдельно требуются rate limiting на вход, журнал доступа к PII с политикой хранения, MFA администраторов, контроль резервных копий, непрерывное управление ключами, TLS, проверка tenancy во всех остальных endpoint, anti-CSRF для междоменных сценариев, load-testing и fuzz-testing.
