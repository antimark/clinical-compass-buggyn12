# Роли, отношения и политика доступа

**Статус:** модель отношений, обязательные клинические шаблоны, индивидуальные права и настройка admin-полей [СОГЛАСОВАНО]. Детали реализации permission-resolution [ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ].

## Не путать роль, членство и связь

- **Роль (`user_role`)** — PATIENT, DOCTOR, RESEARCHER, CLINIC_ADMIN, PLATFORM_ADMIN. Один аккаунт может иметь несколько ролей.
- **Членство (`organization_membership`)** — врач/администратор состоит в конкретной клинике; один врач может работать в двух клиниках.
- **Клиническая связь (`doctor_patient_link`)** — конкретный врач наблюдает пациента в конкретном организационном контексте и по конкретному шаблону.
- **Пациент–клиника (`patient_organization_link`)** — пациент связан с организацией; не эквивалентно праву каждого врача клиники читать его историю.
- **Конфигурация прав (`access_template`, `grants`, `overrides`)** — набор разрешений на *ресурс/поле/операцию* для конкретной связи и пациента.

## Матрица стандартных полномочий (концептуальная)

| Роль | Свой профиль | Чужие клинические данные | Организационные задачи | Stats |
|---|---|---|---|---|
| Patient | Свои разрешённые данные; самоотчёты | Нет | Принятие приглашений и управление согласиями | Нет по умолчанию |
| Doctor | Собственный | Только привязанные пациенты, разрешённые поля | Приглашение пациентов, обязанности в клинике | Только при отдельной независимой выдаче прав |
| Clinic Admin | Свой | Клиника + пациентские идентифицирующие поля **только** по применённой схеме | Сотрудники, лицензии, запись к врачу | Нет по умолчанию |
| Researcher | Свой | Нет доступа к исходным картам | Нет | Только разрешённые опубликованные datasets |
| Platform Admin | Служебные метаданные | Нет содержимого закрытых карт | Управление организациями/лицензиями/служебными объектами | Управление публикацией без произвольного чтения исходных данных |

## Шаблоны врачебного доступа [СОГЛАСОВАНО]

Приглашение пациента содержит выбранный **версионируемый шаблон**: условные `psychiatrist`, `psychotherapist`, `therapist` или `custom`. Названия шаблонов и наборы полей редактируются через БД. Специальность врача сама по себе не даёт дополнительных глобальных полномочий.

**Базовые разрешения шаблона обязательны для данной связи:** пациент видит условия подключения и принимает их при регистрации/привязке. Если обязательные разрешения не предоставлены, связь не активируется. Остальные поля пациент может дополнительно открывать врачу. Пример: психотерапевту отдельно предоставляется `medication_history`; врачу-терапевту не обязательно видеть `homework_completion`.

**Важная реализационная деталь:** действующая ссылка привязана к *версии* шаблона. Изменение шаблона не расширяет незаметно права уже подключённых пациентов. При отзыве права, необходимого для активной обязательной схемы, нужен контролируемый процесс изменения/завершения этой клинической связи, а не обход запрета.

## Clinic Admin и идентифицирующие данные [СОГЛАСОВАНО]

Доступ администратора клиники к `first_name`, `last_name`, `middle_name`, `phone`, `email` и будущим полям — **необязательная** функция, применяемая **отдельно к каждому пациенту в каждой клинике**.

Примеры шаблонов (иллюстративные, не зафиксированный продуктовый перечень):

- `clinic_anonymous`: технический patient reference, статусы запросов на запись, допустимые агрегаты.
- `clinic_limited_registration`: ФИО и сведения, необходимые для организации записи.
- `clinic_contact_registration`: ФИО плюс конкретные разрешённые каналы связи.

Поддержать:

- Изменяемые шаблоны из БД; разные шаблоны для пациентов одной организации.
- Пациент-специфические **дополнения и запреты**.
- Раздельный READ по каждому идентифицирующему полю (и по динамическим полям).
- Глобальный `clinic_admin_identity_access_enabled` и настройку `organization.identity_access_enabled`.
- **Жёсткий запрет доступа при любом выключенном флаге**, включая старые гранты.
- Проверку не только карточки, но и списков, поисковых индексов, сортировки, уведомлений, фильтров, экспортов, API записи, логов.
- Возможность удалить/отключить модуль admin identity без удаления клинических данных.

**Рекомендуемый приоритет политик:** hard deny (флаг, статус, законное ограничение) → проверка связей и условий → явный индивидуальный deny → явно предоставленные разрешения (шаблон и индивидуальные grants) → deny по умолчанию. Это нужно реализовать централизованно и покрыть тестами.

## Предлагаемый контракт авторизатора

```python
check_access(
    principal=user_context,
    action="READ",          # CREATE / READ / UPDATE / DELETE / EXPORT / MANAGE
    resource="patient_fields",
    patient_id="...",
    organization_id="...",
    field_keys=["first_name", "mood_score"],
    purpose="care"            # либо scheduling/research и др.
) -> AccessDecision
```

При READ — возвращать только разрешённые поля **после** проверки видимости объекта; при PATCH — либо весь пакет изменений проходит, либо полная ошибка и откат. Объект не должен раскрывать запрещённые значения через ошибки «field exists», фильтры и выборки.

## Важно: границы «данных врача»

Список `my_patients` — результат активных связей, а не отдельная копия медицинских записей у врача. Врач в клинике A не наследует доступы в клинике B автоматически. История создаётся в контексте автора/клиники/согласий; сведения из другой клиники открываются по соответствующему разрешённому механизму.

## Согласия ≠ технические grants

**Согласие** фиксирует цель, объём, юридически значимое основание/документ, период и статус. **Grant** — техническое разрешение конкретному субъекту на конкретную операцию. При обработке необходимо проверять оба уровня, когда это требуется сценарием.

Разделять: подключение к врачу; передачу истории между клиниками; организационные идентификационные данные; необязательное исследовательское использование. Отказ от исследования не должен автоматически прекращать базовые медицинские отношения.

## Деактивация и замена врачей

Администратор клиники может закрывать организационную связь и освобождать лицензию. При замене врача создаётся **новая** клиническая связь и новые разрешения; старые записи остаются за прежним автором. Передача клинической истории требует разрешённого процесса; «поменять ФИО врача в строке» недопустимо.

## Обязательные негативные проверки

- Роль DOCTOR без связи не читает пациента.
- Разрешён пациент, но не поле: поле не выдаётся.
- READ не даёт WRITE.
- ADMIN не читает диагноз/переписку.
- Выключение флага скрывает ПДн немедленно.
- Сортировка или фильтр по закрытому полю запрещены.
- Отозванный grant и истёкший срок перестают действовать.
- Доступ в одной клинике не переносится на другую автоматически.
