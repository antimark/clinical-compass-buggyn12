# Roadmap: разработка и контрольные точки

**Статус:** [ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ], упорядочено относительно цели сначала получить интегрируемый с Flask каркас. Даты, трудозатраты и команда не утверждены.

## M0 — архитектурный контракт

**Выход:** утверждены роли, отношения врач–клиника–пациент, правила выдачи прав, формат динамических полей, источники данных и договорённость frontend/backend по сессиям, URL и ошибкам.  
**Done:** согласована модель и негативные сценарии доступа; вопросы из `12_РЕШЕНИЯ_И_ОТКРЫТЫЕ_ВОПРОСЫ.md` назначены ответственным.

## M1 — работающий вертикальный сценарий

**Включить:** Flask Application Factory, SQLAlchemy, Alembic, core SQLite; пользователи/роли; клиника/членство; лицензии; приглашение; пациент–врач; шаблон доступа; динамическое поле; write/read с server-side ACL.  
**Демо:** админ создал клинику → выдал ключ врачу → врач связал пациента по шаблону → пациент записал `mood_score` → врач увидел поле → другой врач не увидел.  
**Done:** проходит интеграционный тест и базовый security negative suite.

## M2 — административные операции и права

**Включить:** разные профили врачей, несколько клиник на врача, индивидуальные patient grants, отзыв; clinic-admin identity templates per-patient; global/org kill switches; пациент–клиника, transfer/deactivate, аудит.  
**Done:** отключение identity мгновенно скрывает ФИО во всех списках/экспортах; перенос врача не переписывает авторство.

## M3 — ядро клинических записей

**Включить:** episodes, diagnoses, treatments, medication/prescriptions/intakes, diaries, observations, questionnaires, adverse events, messages и appointments (минимальный согласованный CRUD, версии и ACL).  
**Done:** сценарий дневник → карточка врача → визуализация динамики через API без ручных связок.

## M4 — обязанности хакатона

**Включить:** конфигурируемые шкалы с источниками/версиями и права на использование; клинические источники; правила алертов, надёжная доставка/подтверждение; два уровня маршрутизации; подтверждение врачом; валидные сценарии с «Авиандром»; импорт/извлечение ключевой информации из разных историй болезни для технической метрики.  
**Done:** демонстрационные сквозные клинические сценарии покрывают все 8 функций и обязательные условия `01_КЕЙС.md`, проверки по `11_ТРЕБОВАНИЯ_ТРАССИРОВКА.md`.

## M5 — исследовательский контур

**Включить:** consent registry, publication jobs, политика отбора, отдельные stats SQLite, read-only grants, аудит; на первом шаге — **синтетические наборы**.  
**Done:** researcher может читать выбранный dataset и не может получить core или соседний набор.

## M6 — эксплуатационная готовность

**Включить:** perf/load тесты, backups/restore, RPO/RTO, logging/metrics, security audit, data retention, эксплуатационная документация, юридический/регуляторный анализ.  
**Done:** известны границы нагрузки, есть успешная учебная процедура восстановления и проверенные политики доступа. До production с реальными медицинскими данными все обязательные меры должны быть действительно реализованы.

## Что делать параллельно

| Команда | Работы |
|---|---|
| Frontend | Сценарии пациента/врача/клиники, дизайн системных состояний, mock API, авторизация |
| Clinical | Подбор и проверка валидированных русскоязычных шкал, триггеры рисков, предупреждения, источники |
| Backend | Модели, разрешения, API, миграции, тесты и затем клинические сервисы |
| Data/Research | Форма набора данных, ограничения анонимизации, synthetic demo |
| QA/Security | Негативные тесты прав, попытки IDOR, резервное копирование, аудит |
| Product/legal | Договоры, организация согласий, модель лицензирования и соответствие требованиям |

## Основная зависимость

Нельзя безопасно делать полные API списков пациентов, поиск, экспорт и аналитические отчёты **до** централизованной проверки доступа на уровне полей. Права — часть ядра, не добавка в конце.
