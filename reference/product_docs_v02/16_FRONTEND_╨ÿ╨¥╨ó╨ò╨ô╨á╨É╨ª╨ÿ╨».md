# Интеграция Flask-фронтенда: экраны, состояния и границы доступа

**Статус:** [ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ]. Фронтенд на момент согласования проектируется; это перечень интерфейсных контрактов, а не описание реализованных экранов.

## Общие принципы

- Интерфейс **не является** системой безопасности: сервер всегда перепроверяет операцию, объект, активную организацию и каждое поле.
- Один аккаунт может иметь несколько активных организационных ролей. UI должен явно показывать текущую организацию и контекст роли.
- **Поле недоступно** не тождественно значению `null` или «не заполнено». API и UI согласуют отдельный безопасный способ представления этих случаев.
- Не показывать медицинские значения в поисковых подсказках, браузерном кэше, URL, аналитике фронтенда и уведомлениях, если у получателя нет доступа.

## Минимальные интерфейсы по ролям

| Роль | Экран / действие | Какие API нужны |
|---|---|---|
| Patient | Профиль, история, дневники, ввод показателя | `/patients/me`, field definitions, field values |
| Patient | Приглашения и список врачей | `/invitations/redeem`, `/patients/me/doctors` |
| Patient | Доступы врачам / отзыв дополнительных прав | `/access/effective`, `/access/grants` |
| Doctor | Организации и контекст работы | `/auth/me`, `/organizations/.../members` |
| Doctor | Список своих пациентов и карточка | `/doctors/me/patients`, разрешённые fields |
| Doctor | Создание приглашения с шаблоном | `/access-templates`, `/invitations` |
| Doctor | Наблюдения и события риска | `clinical`, `alerts` |
| Clinic Admin | Сотрудники, лицензии, приглашения | `/organizations/.../members`, `/licenses`, `/invitations` |
| Clinic Admin | Список на запись | `appointments`, per-patient identity ACL |
| Platform Admin | Организации, договоры и настройки | `admin`, `organizations`, `license-settings` |
| Researcher | Каталог доступных наборов и анализ | `/research/datasets`, `/research/datasets/{id}/records` |

## Ключевые UI-состояния

- `loading`, `empty`, `validation_error`, `not_authenticated`, `forbidden`, `expired_invitation`, `revoked_invitation`, `license_limit_reached`, `organization_inactive`, `consent_required`, `permission_revoked`, `temporarily_unavailable`.
- После отзыва разрешения сведения должны исчезать из UI при следующей актуализации; не полагаться только на клиентскую фильтрацию.
- Системные сигналы `critical`, `обязательно`, `желательно` должны быть различимы; alert требует статуса доставки и подтверждения, не просто декоративного бейджа.
- При клинической записи отмечать: источник, время наблюдения, автора, статус подтверждения (если решение врачебное).

## Предпочтительный рабочий процесс подключения

1. Принять `/api/v1` и схему `error` (см. `07_API_КОНТРАКТ.md`).
2. Сгенерировать seed **синтетических** пользователей и сценариев A–J (`10_ТЕСТЫ_ПРИЁМКА.md`).
3. Сделать интерактивный путь clinic → doctor → invitation → patient → dynamic field → doctor view.
4. Добавить тест на запрещённое поле и выключенный clinic-admin identity flag.
5. Только после этого расширять экраны исследования и клинических рекомендаций.

## Что согласовать между командами

Транспорт сессий и CSRF; формат временны́х рядов и таймзон; методы просмотра «право запрещено/данные отсутствуют»; поля в пагинации; наличие поля и его значение; момент переключения клиники; ограничения выгрузки; редактирование vs добавление новой версии; реальное время/период опроса алертов.
