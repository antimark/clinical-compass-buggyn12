# Архитектурные решения и незакрытые вопросы

**Состояние на 17.10.2026.** Отделяет [СОГЛАСОВАНО] от [ОТКРЫТО] и проектных рекомендаций.

## Принятые решения [СОГЛАСОВАНО]

| ADR | Решение | Причина |
|---|---|---|
| ADR-01 | Одна общая `core.sqlite` на платформу | Единый пациент между клиниками; врач работает в нескольких организациях |
| ADR-02 | Отдельные stats SQLite для researcher | Исследователям нельзя давать доступ к исходным картам |
| ADR-03 | Модульный бэкенд на Flask, SQLite, с дальнейшим расширением | Интеграция с проектируемым Flask UI, невысокий порог MVP |
| ADR-04 | Шаблоны доступа настраиваются в БД | Различные специальности, разные права на разных пациентов |
| ADR-05 | Базовый шаблон обязателен для активации соответствующей связи | Иначе не работает клинический сценарий обслуживания |
| ADR-06 | Дополнительные разрешения пациент предоставляет отдельно | Не все данные одинаково нужны врачам разных направлений |
| ADR-07 | Clinic Admin имеет per-patient настраиваемый доступ к ФИО/контактам | Запись к врачу иногда требует ПДн, но функция должна отключаться |
| ADR-08 | Global/org флаги могут полностью выключить identity-read для Clinic Admin | Безопасное отключение функции без перестройки клинической БД |
| ADR-09 | Лицензии — конфигурируемые врачебные места по договору | «30» — пример, не константа |
| ADR-10 | Приглашения соединяют существующие или новые профили | Не создавать дубли пациентов/врачей |
| ADR-11 | Удаление клиники/отвязка пациента не уничтожает автоматически общую историю | Сохранение динамики и смена учреждения |
| ADR-12 | Исследовательские выборки только через контролируемый pipeline | Проверки прав, оснований и минимизации данных |
| ADR-13 | Обратимо защищённые значения ≠ хеши | Для восстановления нужны шифрование/управляемая псевдонимизация |
| ADR-14 | Врач подтверждает назначения/клинические действия | Обязательное условие задания |

## Проектные рекомендации, ещё не утверждённые как окончательные

- SQLAlchemy 2, Alembic, модульный монолит и Flask Application Factory.
- Immutable версии шаблонов, grants/denies и единый Permission Engine.
- `outbox` для гарантируемых попыток доставки алертов.
- Разделение файлового хранилища и метаданных БД.
- Модель шифрования и хранения ключей вне `core.sqlite`.
- Журналирование сущностей и решения об удалении вместо физического каскада.
- Наличие read-model для тяжёлой аналитики.

## Вопросы, требующие решения до реальных медицинских данных [ОТКРЫТО]

1. **Формы юридически значимого согласия:** какие именно акцепты допустимы, когда нужна специальная форма, кто оператор данных, порядок отзыва и сроки хранения.
2. **Точная модель ownership/custodianship:** кому принадлежат и кем вносятся клинические записи разных организаций; перенос истории между клиниками.
3. **Конкретные стандартные шаблоны врачей:** какие поля обязательны для психиатра, психотерапевта, терапевта; кем утверждаются изменения.
4. **Границы администрирования:** кто может выдавать admin identity-шаблоны, как пациент получает прозрачное уведомление и контролирует переопределения.
5. **Наследование согласий и новых правил:** как мигрировать разрешения при смене шаблона или условий договора.
6. **Физическое удаление и хранение:** условия архивирования и удаления клинических записей, логов и backup при окончании договора.
7. **Управление ключами шифрования:** среда исполнения, ротация, восстановление и разграничение доступа к ключам.
8. **Политика статсов:** какие наборы допустимы, как проверяются малые группы и отдельные клинические кейсы, кто утверждает публикацию.
9. **Alert delivery:** конкретные клинические признаки, каналы, дежурства, SLA, алгоритм эскалации при неотвечающем враче.
10. **API auth:** cookie sessions/CSRF, варианты мобильного клиента, multi-role переключение и trust boundary.
11. **MVP критерии нагрузок:** целевой concurrent users, p95, RPO/RTO, размеры динамических временных рядов.
12. **Клиническая валидация:** конкретные русскоязычные шкалы и права их использования; текущие ГРЛС/рекомендации.
13. **Проверка требований по российскому регулированию** и квалификация ПО как медицинского изделия, если применимо.
14. **Дедупликация профилей** при приглашении уже зарегистрированного пациента; без утечки существования аккаунта.

## Принцип разрешения противоречий

При расхождении текста задания и концепции **обязательные требования кейса** определяют то, что нужно продемонстрировать для хакатона. Согласованная архитектура определяет способ реализации. Если детали ещё не согласованы, записывать их как [ОТКРЫТО], а не подменять произвольной реализацией.
