# Пользовательские сценарии Clinical Compass

**Источники:** исходная концепция (восемь продуктовых сценариев) [КОНЦЕПЦИЯ], официальный клинический кейс [КЕЙС] и согласованные сценарии регистрации/прав/лицензий [СОГЛАСОВАНО]. Сценарии описывают *целевое поведение*, а не текущий статус реализации.

## UC-01 — регистрация врача в клинике

**Участники:** Clinic Admin, Doctor.  
**Предусловие:** активный договор и свободное лицензионное место.  
**Шаги:** администратор генерирует приглашение → новый или существующий врач принимает приглашение → создаётся активное организационное членство → место закрепляется.  
**Ожидается:** один аккаунт врача, корректный счётчик лицензий, токен нельзя применить повторно.  
**Исключения:** срок приглашения истёк; лимит достигнут; организация заблокирована.

## UC-02 — врач в двух клиниках

**Участники:** Doctor, Clinic A, Clinic B.  
**Шаги:** один врач принимает приглашения из двух клиник → видит два контекста работы → выбирает контекст при действиях.  
**Ожидается:** данные пациента/членства не смешиваются; доступ в одной клинике не наследуется во вторую.

## UC-03 — пациент подключается к психиатру по шаблону

**Участники:** Doctor (psychiatrist), Patient.  
**Шаги:** врач выбирает шаблон `psychiatrist` → создаёт приглашение → пациент изучает обязательный набор и принимает условия → связь `doctor-patient-org` активируется.  
**Ожидается:** пациент появляется в выборке врача, врач видит только разрешённые поля; без обязательного набора связь не активируется.

## UC-04 — один пациент, два врача, разные разрешения

**Участники:** Patient, Psychiatrist, Psychotherapist.  
**Шаги:** психиатр видит медикацию и динамику; психотерапевт по своему шаблону — динамику и домашние задания; пациент дополнительно разрешает психотерапевту читать медикацию.  
**Ожидается:** дополнительные поля открываются только конкретному врачу; другой врач не получает их автоматически.

## UC-05 — отзыв разрешения

**Участники:** Patient, Doctor.  
**Шаги:** пациент отзывает дополнительный READ на `medication_history` → врач повторяет GET/поиск/экспорт.  
**Ожидается:** значение немедленно исчезает из последующих ответов и поисковых/экспортных результатов; обязательность базового шаблона не обходится.

## UC-06 — конфигурируемая регистрационная информация для клиники

**Участники:** Clinic Admin, два пациента.  
**Шаги:** пациенту A применена схема с ФИО и телефоном, пациенту B — анонимная; администратор открывает список записей на приём. Затем владелец системы отключает организационный identity feature flag.  
**Ожидается:** до отключения разные поля по каждому пациенту; после отключения — ни одно идентифицирующее поле не выдаётся, а операция записи остаётся возможной через внутренний id.

## UC-07 — пациент перестал посещать клинику

**Участники:** Clinic Admin, Patient.  
**Шаги:** организация деактивирует связь пациент–клиника → завершаются зависимые разрешения этой организации.  
**Ожидается:** клиника больше не видит пациента вне разрешённых исключений; глобальный профиль и законно хранимая история остаются.

## UC-08 — увольнение врача и передача пациентов

**Участники:** Clinic Admin, старый и новый врач, Patient.  
**Шаги:** закрыть организационное членство → освободить место → инициировать разрешённый процесс переприкрепления → создать новые связи и разрешения.  
**Ожидается:** старые назначения продолжают ссылаться на реального прежнего автора, никакой замены профиля «внутри записей».

## UC-09 — мониторинг медикаментозной терапии [исходная концепция]

**Участники:** Doctor, Patient.  
**Шаги:** врач подтверждает назначение → пациент фиксирует приём, сон, настроение и самочувствие → система строит динамику → врач оценивает ситуацию.  
**Ожидается:** измерения отмечены датой/источником, доступны разрешённому врачу, терапия не меняется автоматически.

## UC-10 — возможное нежелательное явление [исходная концепция]

**Шаги:** пациент сообщает симптом и время его появления → создаётся adverse_event → при срабатывании правила создаётся alert → врач оценивает и решает о действиях, включая официальное сообщение при необходимости.  
**Ожидается:** событие не выдаётся за доказанную причинную связь с препаратом.

## UC-11 — мониторинг психотерапии [исходная концепция]

**Шаги:** пациент выполняет разрешённые задания, фиксирует самочувствие → психотерапевт видит динамику/выполнение заданий → оценивает её.  
**Ожидается:** врач-терапевт без разрешения не видит содержимое заданий, а динамика сама по себе не доказывает эффективность метода.

## UC-12 — сигнал ухудшения и запись [исходная концепция + кейс]

**Шаги:** пациент заполняет опросник → правило фиксирует тревожную динамику → формируется предупреждение и попытка доставки врачу → врач подтверждает получение и решение → при необходимости формируется запрос на запись.  
**Ожидается:** у alert есть статусы доставки/подтверждения; Clinic Admin видит ровно данные, необходимые для координации записи, если они разрешены. Нет обещания немедленного врачебного ответа без дежурства.

## UC-13 — стандартизированный психометрический опрос [кейс]

**Шаги:** пациент проходит русскоязычную валидированную шкалу → система сохраняет версию формы, исходные ответы, метод расчёта, балл → врач видит динамику и источник/ограничения.  
**Ожидается:** шкалу можно обновить версионно; нельзя незаметно пересчитать старые ответы по новым правилам.

## UC-14 — рекомендация по маршрутизации к психиатру [кейс]

**Шаги:** анализ разрешённых показателей → система формирует сигнал «обязательно» или «желательно» с объяснением → врач рассматривает предложение → подтверждает решение.  
**Ожидается:** сигнал не равен автоматическому направлению.

## UC-15 — демонстрация препарата «Авиандр» [кейс]

**Шаги:** синтетический профиль пациента → корректный клинический контекст и справочный материал по действующим источникам → предложение/обсуждение терапии → решение врача → мониторинг и маршрутизация.  
**Ожидается:** в демонстрации есть профиль, терапия и маршрутизация. Назначения и режимы дозирования требуют проверки по действующему ГРЛС и клиническим рекомендациям до показа.

## UC-16 — отчёт исследователю по медикации [исходная концепция + согласованные решения]

**Участники:** Platform Admin, уполномоченные лица/оператор данных, Researcher.  
**Шаги:** проверка разрешений и договоров → допустимая выборка исходных клинических данных → контроль повторной идентификации → публикация набора в отдельную stats DB → grant конкретному исследователю.  
**Ожидается:** исследователь может читать разрешённые поля/интервалы/кейсы; исходные IDs и карточки недоступны; причастность лекарства не трактуется как доказательство эффекта.

## UC-17 — доступ к собственной истории [исходная концепция]

**Шаги:** пациент открывает историю прошлых курсов, назначений, опросников и подтверждённых советов → передаёт выбранные сведения новому врачу по разрешённой процедуре.  
**Ожидается:** сохраняются дата, автор, контекст клиники, происхождение записи.

## UC-18 — вовлечение пациента [исходная концепция]

**Шаги:** приложение показывает частоту заполнений, напоминания и нейтральную визуализацию.  
**Ожидается:** механика не стимулирует скрывать симптомы или «соревноваться» за хорошие показатели.

## UC-19 — клинический импорт (отдельная оцениваемая метрика кейса)

**Шаги:** команда импортирует синтетические истории разной структуры → парсер формирует структурированные сущности, в том числе диагнозы и назначения → показывается evidence/source и качество извлечения.  
**Ожидается:** результаты подлежат проверке; импорт не создаёт автоматически подтверждённые врачом решения.

## Примечание о статусе

UC-09–19 требуют отдельной клинической и UX-реализации. Наличие таблиц `alerts` и `questionnaires` в первом каркасе ещё не означает выполнение всего сценария.
