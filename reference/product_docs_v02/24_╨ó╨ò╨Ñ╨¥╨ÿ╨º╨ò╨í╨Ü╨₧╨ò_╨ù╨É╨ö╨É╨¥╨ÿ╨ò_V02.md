# 24. Техническое задание Clinical Compass v0.2

**Для обсуждения и декомпозиции с двумя разработчиками.** 10 дней / 5 участников / Flask + Jinja2 + SQLAlchemy + SQLite / только синтетика. Слово «должен» — требование, **не реализация**. Базовые документы: `01`, `03`–`07`, `10`, `11`, `21`–`23`.

## 0. Definition of Success

Один полностью воспроизводимый демо-прогон: пациент входит → короткий check-in / валидированный опросник / сообщение о приёме лекарства → у связанного врача обновляется динамика → правило создаёт сигнал → врач видит его сверху и подтверждает оценку → назначает pre-visit опросник → пациент получает задачу → встроенный demo чат-бот помогает сформулировать наблюдение → врач получает **отдельно разрешённую** сводку/заметку → исследователь фильтрует собственный синтетический dataset.

В демонстрации **обязательно** показать отдельный клинически проверенный сценарий с препаратом «Авиандр», ссылки на действующие источники, две категории маршрутизации и одобрение/отклонение решения врачом. AI/Research не вправе «съесть» сроки обязательных восьми функций.

## 1. Технологическая структура

```text
clinical_compass/
  app/
    __init__.py                    # create_app, blueprint registration
    config.py
    extensions.py                  # db, session, migrations
    models/                        # SQLAlchemy 2 models, migrations
    auth/                           # login, session, role/org context
    permissions/                    # can_read/can_write/filter_fields
    doctor/                         # views + services + API
    patient/                        # views + services + API
    clinic/                         # appointments/membership
    research/                       # only stats read API
    questionnaires/                 # catalog/responses/scoring
    medications/                    # prescription and intake self-report
    alerts/                         # rules, events, outbox, acknowledge
    appointments/                   # visits, requests, scheduling
    messages/                       # doctor/patient messages
    ai/                             # service, adapter, safe_fallback, evals
    audit/                          # metadata-only audit
    templates/                      # Jinja layouts by role
    static/css, static/js
  data/core.sqlite                  # no live patient data in demo
  data/stats/synthetic_demo.sqlite  # isolated research snapshot
  tests/
  scripts/seed_demo.py
  docs/
```

SQLite режим WAL, `foreign_keys=ON`, timeout, короткие транзакции. Клинические назначения/решения/сводки версионируются. Для разового демо фоновые процессы можно имитировать локальным синхронным service function **с явным статусом фактической доставки в inbox**, но нельзя выдавать запись `outbox` за успешно доставленное уведомление.

## 3. DTO-соглашения и безопасность

- У каждого клинического события: `id, patient_id, author_id, observed_at, recorded_at, source_type, version, status, organization_id, provenance`.
- В API есть `capabilities` для допустимых операций, но **не** скрытые значения. `field_visibility` вычисляется сервером.
- Сборка любого списка, графика, поиска, score/delta, summary, CSV проходит после фильтрации по правам.
- Нет данных: `unknown`, не `normal` или `zero`; интервал ретроспективного самоотчёта не разбрасывать на даты.
- Автором подписанной записи является врач, а AI-черновик хранится отдельно.
- Исследователь не обращается к core.sqlite; только отдельный synthetic stats dataset.
- Сессии: HttpOnly/SameSite, CSRF на POST/PATCH, пароли/ключи вне репозитория; синтетический демо-login — только для локального окружения.

## 5. Endpoint requirements (subset `/api/v1`)

| Метод / путь | Действие | Проверка |
|---|---|---|
| `GET /doctors/me/patients?sort=attention&q=...` | Список врачебных пациентов | Отбор связанных и разрешённых до сортировки |
| `GET /doctors/me/patients/<id>/overview` | Карточка с доступными modules/capabilities | 403/404 чужому врачу, отсутствие скрытых полей |
| `GET /doctors/me/alerts` | Critical/other alert inbox | Только разрешённые сигналы |
| `POST /alerts/<id>/acknowledge` | Отметка получения | timestamp+actor+audit |
| `POST /alerts/<id>/assessment` | Оценка и следующее действие | Decision is human actor, not AI |
| `POST /patients/me/check-ins` | Mood and comparison | Ввод только своего пациента |
| `POST /patients/me/questionnaires/<id>/responses` | Ответ на назначенную шкалу | Schema/score version, валидированный алгоритм |
| `POST /patients/me/medication-reports` | Принятие/пропуски | Separate daily and approximate intervals |
| `POST /appointments/requests` | Запрос пациентом | Связь с врачом, статус requested |
| `POST /questionnaire-requests` | Задача врача | Разрешение CREATE, notification inbox |
| `POST /messages` | Передача сообщения | Check participants and active link |
| `POST /doctor/patients/<id>/encounters` | Заметка врача | Draft vs signed |
| `POST /ai/chat` | Текстовая демо поддержка | Auth, limited context, safety fallback, kill switch |
| `POST /ai/summaries` | Черновик резюме | Source ids scoped via permissions |
| `POST /ai/summaries/<id>/confirm` | Врач утверждает | Edited/confirmed text saved, not raw draft |
| `GET /research/datasets` | Разрешённые наборы | No core patient data |
| `GET /research/datasets/<id>/cohort` | Prepared safe filtered stats | Whitelist fields, query params and row limit |
| `GET /research/datasets/<id>/aggregate.csv` | CSV | Aggregates only, privacy thresholds |

Существующий `07_API_КОНТРАКТ.md` остаётся базой; таблица выше — приоритетная дельта, не полная независимая замена.

## 6. Динамические интерфейсы без динамических утечек

- Server builds `ui_sections` as ordered list based on `specialty_view_config` and filtered `capabilities`.
- E.g. psychiatric doctor: trends, medication, physical issues, side effects, appointments. Psychotherapy specialist: symptoms, behavioral program, homework, sessions. Psychologist: self-reports/session plan (не «назначение лекарств»). Neurologist — feature flagged future configuration.
- User may collapse/reorder allowed sections, but cannot grant self access.
- UI `hidden_by_preference` ≠ server `not_authorized` ≠ `unknown/not_recorded`. Only `not_authorized` prevents data serialization; UI may show a neutral permissions explanation if policy allows revealing the existence of that category.

## 7. Демонстрационные данные и сценарии

**Seed:** минимум 2 врача разных профилей; пациент A с двумя врачами и частично скрытой medication history; пациент B с ухудшением и синтетическим critical event; пациент C со стабильной динамикой; пациент D с ретроспективным adherence; минимум 1 clinic admin, 1 researcher, 1 stats dataset (обученная синтетика). Сценарий «Авиандр» формируется только после review специалистов и ссылки на действующую инструкцию.

**Demo path:** переключить роль → пациент check-in → врач увидел изменение → показал отличие разрешений → запросил шкалу к визиту → пациент выполнил → врач проверил результат → AI-chat пациенту и человек-reviewed summary → исследователь изменил фильтр и число когорты/график реально обновились.

## 8. Нефункциональные требования

- Startup одним набором команд; `seed_demo` воспроизводим без ручной правки SQLite.
- Тесты `pytest` для ACL/CSRF/IDOR и эндпоинтов критических действий.
- Целевой UX: patient check-in не более 3 шагов, открытие карточки из поиска за 2 действия; замерить, не выдавать нормативы за требование кейса.
- Чётко видимые статусы загрузка/ошибка/пусто/нет данных/не разрешено.
- Desktop-first doctor/research, mobile-first patient, responsive clinic.
- Все даты в БД UTC; UI форматирует по выбранной таймзоне.
- Privacy: логи не содержат текста медицинских сообщений, prompt и raw patient data; в демо synthetic watermark.
- Процедура backup/restore хотя бы в демонстрационном окружении.

## 9. Definition of Done P0

1. `python scripts/seed_demo.py` создаёт роли, разрешения, пациентов и события.
2. Два разных врача получают разные безопасные DTO одного пациента; запрещённое medication поле отсутствует в payload и AI-summary.
3. Пациентский self-report реально сохраняется, врача обновляет запрос к API.
4. Одна проверенная русскоязычная шкала корректно считается, показывает версию и источник.
5. Фактический intake и ретроспективные записи показаны без фабрикации пропусков.
6. Есть сценарий с проверенными ссылками для «Авиандр» и отдельным человеческим подтверждением маршрутизации/решения.
7. Critical event → alert event → попытка inbox/outbox доставки → ack в БД; не просто нарисованный красный блок.
8. Встроенный пациентский бот работает по сценарному demo adapter; тестирует отказ от назначения дозы и безопасный fallback.
9. AI-summary как отдельный draft или честно помечено `INFRA_ONLY`, если интеграции нет; подтверждённое врачом сообщение сохраняется отдельно.
10. Демо исследователя действительно меняет данные при фильтрации synthetic stats.
11. Показаны результаты автоматических тестов, ограничения и отсутствующие функции.
