# Контекст для нового чата: продолжение разработки или независимое ревью

Скопируйте этот файл в начало нового чата вместе с кодом/ZIP и нужными разделами документации.

## Передаваемый контекст

**Проект:** Clinical Compass — цифровой ассистент врача и платформа клинического мониторинга пациентов. Основной сценарий хакатона — пациенты с тревожной и депрессивной симптоматикой. Исходный официальный кейс требует шкалы, справочную информацию по терапии, риски/нежелательные явления, динамику, самоотчёт, связь с врачом, приверженность, маршрутизацию к психиатру с категориями «обязательно/желательно», критические алерты и контроль врачом всех назначений/изменений. В демонстрации рассматривается «Авиандр»; использованные клинические источники и русскоязычные шкалы должны быть актуальными и валидированными.

**Текущая инженерная задача:** строится **бэкенд-каркас**, не заявляется законченная клиническая система. Flask + SQLite + SQLAlchemy (рекомендуемо), модульный монолит, REST API, миграции и тесты. Одна общая `core.sqlite`, потому что один врач работает в разных клиниках, а пациент имеет единую историю и нескольких врачей. Отдельные `data/stats/*.sqlite` — для опубликованных исследовательских наборов, с индивидуальными researcher grants.

**Роли:** PATIENT, DOCTOR, RESEARCHER, CLINIC_ADMIN, PLATFORM_ADMIN; один человек может иметь несколько ролей и организационных членств. Doctor видит пациентов по активным связям и поля по индивидуально применённым версионируемым шаблонам. Обязательный базовый шаблон принимается пациентом при подключении; дополнительные разрешения пациент предоставляет отдельно. Разрешения READ/WRITE на уровне полей; default deny. Clinic Admin управляет лицензиями и записью, а доступ к ФИО/контактам **конфигурируется по пациенту**, может быть полностью выключен глобально или для конкретной клиники. Platform Admin управляет объектами без чтения исходных закрытых клинических данных.

**Регистрация:** договор определяет любое число врачебных лицензионных мест (число 30 было лишь примером). Ключи-приглашения привязывают врача к клинике, пациента к врачу по выбранной схеме, в т.ч. уже существующие профили. Уволенный врач освобождает место, но его историческое авторство не подменяется. Отвязка пациента от клиники не уничтожает его глобальную историю.

**Data:** нормализованные таблицы + динамические клинические поля с типом, валидатором, версией, категорией и чувствительностью; новые поля должны добавляться без переписывания Permission Engine. Клинические API должны учитывать field-level ACL в GET/PATCH/поиске/экспорте.

**Privacy/research:** исследовательские наборы создаются после проверок допустимости, согласий и минимизации; researcher не имеет доступа к core. Хеширование необратимо; для обратимой защиты нужны шифрование или контролируемая псевдонимизация. Анонимизация требует отдельной проверки повторной идентификации. Для раннего прототипа использовать только синтетические данные.

**Источники:** `sources/Кейс_цифровой_помощник_клинический_компас.pdf` и `sources/Предварительная_концепция_продукта.docx`. В каталоге `docs/` — отдельные файлы по требованиям, модели, API, UX и проверкам. Не считайте проектные рекомендации уже реализованным кодом.

## Инструкция для чата-разработчика

> Изучи переданные документы и фактический код. Разработай следующий вертикальный рабочий модуль без переписывания остальных частей. Поддерживай единый реестр динамических полей и централизованные проверки доступа. Каждый endpoint должен иметь тест для разрешённого и запрещённого сценария; не использовать реальные медицинские данные. Отмечай реализованное, не реализованное и риски. Прежде чем менять интерфейс между frontend/backend, дай список изменений контракта.

## Инструкция для независимого ревью

> Проведи проверяемое техническое ревью исходного кода по требованиям пакета. Сначала установи зависимости и запусти тесты, если среда позволяет. Сравни реальные модели/API/permissions с `03`–`11`. Обязательно проверь межклинические связи, лимиты лицензий, историческое авторство, динамические поля, права врача по каждому пациенту, раздельный per-patient identity доступ Clinic Admin, мгновенное действие feature flags, изоляцию research stats и отсутствие утечек через списки/фильтры/экспорт. Для каждого дефекта дай файл, функцию, способ воспроизведения, приоритет P0–P3 и минимальный патч/тест. Не утверждай, что тест пройден, если не запускал его. Отделяй невыполненную инфраструктуру от необязательных на данном этапе клинических модулей.

## Что приложить для реального ревью

1. Репозиторий/ZIP с исходниками и миграциями (без `.env` с секретами, реальных БД и PHI).
2. `pytest` вывод, инструкции запуска и seed с синтетическими пользователями.
3. Требования `01`, `03`, `04`, `05`, `10`, `11` и список открытых решений `12`.
4. Известные ограничения и цель текущего релиза.
