# Предлагаемая модель данных SQLite

**Статус:** логическая спецификация [ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ], согласованная по принципам: единый профиль, клиники как отношения, гибкие поля и разрешения [СОГЛАСОВАНО]. Имена таблиц предварительные; они не означают существующий код.

## Принципы

1. Нормализованные базовые сущности + динамический реестр полей и значений, **не превращать всю БД в бесконтрольный JSON/EAV**.
2. Один `user_id` может иметь несколько ролей/организаций; один `patient_id` — несколько врачей.
3. Связи имеют статус, периоды действия и контекст организации.
4. Каждая клиническая запись знает пациента, создателя, происхождение (source), время события и техническое время записи.
5. Права отделены от физического места хранения; независимые grants не копируют саму запись.
6. Исторические назначения не меняют автора при переводе пациента.

## 1. Идентичность и организации

| Таблица | Назначение / важные поля |
|---|---|
| `users` | id, auth_subject/email_login (если применяется), status, timestamps; идентифицирующие поля не выставлять без ACL |
| `roles`, `user_roles` | роль пользователя и контекст, если используется составная модель |
| `patient_profiles` | id, user_id unique, технические атрибуты, идентифицирующие значения защищены/разрешаются отдельно |
| `doctor_profiles` | id, user_id unique, профиль специалиста; специальность — справочник/связь |
| `doctor_specialties` | связка врач–специальность, подтверждённые квалификации при необходимости |
| `organizations` | id, name, type, status, contract metadata |
| `organization_memberships` | user_id, org_id, organization_role, active_from, active_to, status |
| `patient_organization_links` | patient_id, org_id, active_from/to, status, основание/источник |
| `doctor_patient_links` | patient_id, doctor_id, org_id, access_template_version_id, status, started/ended |

**Не делать** `doctor.organization_id` единственным FK, иначе врач не сможет работать в нескольких клиниках.

## 2. Договоры и приглашения

| Таблица | Назначение |
|---|---|
| `organization_contracts` | срок договора, состояние, версии условий, лимиты/фичи |
| `license_allocations` | org_id, membership_id, тип лицензии, active_from/to; уникальность активной аллокации |
| `invitation_tokens` | token_hash/HMAC, issuer_id, kind, org_id, target_doctor_id, template_version_id, expiry, used/revoked |

Количество лицензий должно вычисляться из **активных мест**, сравниваться с конфигурацией договора внутри защищённой транзакции. Не хранить «30» в константе продукта.

## 3. Управление доступом

| Таблица | Назначение |
|---|---|
| `field_definitions` | ключ, тип, категория, версия, правила валидации, уровень чувствительности |
| `access_templates` | имя шаблона, область применения (doctor/clinic-admin), статус |
| `access_template_versions` | неизменяемое содержимое версии и дата публикации |
| `template_field_permissions` | версия, resource, field_key, action, mandatory, allow/deny |
| `access_grants` | principal/scope, patient_id, org_id, field/resource/action, granted_by, validity, revocation |
| `access_denies` | точечные ограничения с приоритетом над grants |
| `feature_flags` | глобальный/организационный запрет идентифицирующего доступа |
| `consents` | subject, purpose, legal_basis/document_version, scope, validity, status, withdrawal |
| `audit_events` | who/when/what/object/result/основание, без значения закрытого поля |

Нужна однозначная модель **effective permissions**, учитывающая версию шаблона, hard deny, тип ресурса и связь.

## 5. Динамические поля

Предлагаемая модель:

- `field_definitions`: стабильный `field_key`, например `mood_score`; тип, категория и уровень чувствительности.
- `field_definition_versions`: неизменяемые снимки валидации, единиц, allowed values и метаданных.
- `dynamic_field_values`: id, patient_id, owner_record_id/record_type, field_definition_version_id, value_json (валидированный тип), recorded_at, created_at, created_by, provenance, organization_id, status.
- Индекс `(patient_id, field_definition_version_id, recorded_at)`; при объёмах — отдельные read-модели/агрегаты.

**Пример:** добавляем `homework_completion` через регистрацию поля; пишем новое значение для пациента; выдаём доступ врачу-психотерапевту; врач-терапевт это поле не получает. Для значений `json/text` нужны дополнительные проверки вложенных чувствительных полей и политики на контейнер.

## 6. Research datasets

- `research_datasets`: id, publication_status, dataset_uri, schema_version, owner, scope, publication_date, expiry, deidentification_version.
- `research_access_grants`: researcher_id, dataset_id, resource/table/view, read scope, expiry.
- `research_publication_jobs`: кто запустил, юридическое/техническое основание, выборка, чек-лист приватности, статус.
- `pseudonym_mappings`: **не внутри** исследовательского файла; отдельно защищённая таблица соответствий только для разрешённых внутренних целей.

`data/stats/<dataset-id>.sqlite` содержит **только опубликованные** аналитические таблицы/кейсы с разрешённым составом полей. Передача исследователю файла непосредственно не предполагается по умолчанию.

## Ключи и ограничения

- UUID/ULID или другой стабильный неперсональный идентификатор — [ПРОЕКТНОЕ ПРЕДЛОЖЕНИЕ].
- Уникальные пары активного членства и связей (включая контекст), без физического удаления истории.
- FK `ON DELETE` нужно выбирать исходя из жизненного цикла: нельзя каскадно уничтожать историю пациента из-за удаления организации.
- Время хранить единообразно (UTC + timezone в клиенте), различать время наблюдения и записи.
- Значимые изменения — аудит и версионирование, а не молчаливый overwrite.

## Почему таблицы «только по списку» недостаточно

Требуется выделять **объектные**, **полевые** и **операционные** разрешения: доступ к `diagnoses` не следует автоматически из возможности видеть `patient_id`; право читать `medication_history` не равно возможности редактировать `prescriptions`; доступ к клинике не равен доступу ко всем пациентам клиники.

## Открытые детали

Правила объединения записей между клиниками, owner/custodian записей, регуляторные сроки хранения, транзакционный формат массового перевода пациентов, точные уровни чувствительности, схема идентификации пациента, юридическое основание использования для исследований — требуют отдельного утверждения.
