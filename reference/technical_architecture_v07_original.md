# Technical architecture v0.7 — integration and security

## What has actually been integrated

- Python Flask/SQLAlchemy API starter v0.3, including original check-in, doctor list, alerts and server session/CSRF paths.
- Extension models and API for hashed, expiring, one-use invitation codes; patient-facing previsit snapshot; restricted case message history with one-message-before-reply policy; offered appointments and patient confirmation; pair-specific shared patient visibility; audit logs; synthetic research aggregates.
- Buggy original static styles/templates/JS preserved under `reference`; v0.6 interactive mockup served by Flask at `/` using its own JS demo state. Flask serves the separate **real backend** interface at `/api-lab.html` for cross-role end-to-end verification.
- Clinical admin PII module source in `reference/admin_pii_module`: **reference implementation only, not integrated into live Flask service**. Its own migrations, service and policy tests must be reconciled with the single SQLAlchemy model before any real PII workflow.

## Server data and privacy boundaries

`User` (role) + `DoctorPatientLink` (patient-specific data categories) is the foundation; current new `PrevisitCase` has immutable submitted JSON intake and `allowed_until`; Case IDs are opaque random values. A physician may read ONLY cases where `doctor_id == session.user_id`; consent to previsit does not enable a query for full chart. Related chat and appointment objects are scoped by case/actor. For shared patients the patient must have TWO active doctor links and a `CareTeamVisibility` record for the exact doctor pair. Public doctor DTOs omit patient identity. Research API returns solely synthetic cohort aggregates. State transitions and reads write minimal synthetic audit entries (case read, invitation issued/redeemed, message sent, appointment changed).

### Pseudonymization (planned security step; demonstration today)

Fixtures already use pseudonymous technical keys (`pat_a`, `pat_b`) and synthetic display names, not real people. **That is not enough for real pseudonymization**. Production must isolate identity/contact/PII into a separately encrypted identity vault or database; core clinical tables use random internal patient IDs, and a mapping table in a separately controlled security boundary links identity to clinical ID. Research analytics must use a different, study-scoped pseudonym with independently keyed deterministic derivation (e.g. HMAC-SHA256 with a secret per study and rotation policy), never reuse the clinical patient ID as a public research identifier. Treat pseudonymized health data as personal data under GDPR. Apply minimization, separation of duties, masking, purpose-bound authorization, access logs and retention controls; test re-identification risks and small cohort disclosures before export. Raw identifiers must never be logged in application telemetry.

### Authentication, permissions, key management

The starter **does not implement password-based registration or production-grade auth**. Synthetic demo role switching at `/api/v1/dev/switch-user` works ONLY when `CC_DEMO_MODE=1`. For real deployment: OIDC/passkeys/password storage with Argon2id, MFA for clinicians/admins, verified credentials and invitation-bound onboarding. Sessions need HTTPS, secure cookies and short TTL; CSRF is currently checked on unsafe `/api/v1/` actions except the deliberately synthetic-only demo role switch. Privilege checks happen on the server, not in JS.

Codes:
- Doctor → patient: `POST /api/v1/invitations` as doctor with `target_role:patient`, `patient_id`, category subset. Patient account with matching patient_id redeems at `POST /api/v1/invitations/accept`.
- Clinic admin → doctor: `target_role:doctor` (issuance and single-use validation are implemented; account provisioning/verification is NOT implemented).
- Platform admin → clinic admin: `target_role:clinic_admin` (same demo-only limitation).
- Codes are generated by `secrets.token_urlsafe(24)`, SHA-256 digests stored in DB, one-use, expire after seven days; plaintext shown once to issuer and never logged. A code is not an authentication factor: production invitations must bind to verified contact/identity, require authenticated recipient and audit, rate limits, transactional redemption and revocation. Current sample is not race-safe for multiworker concurrency; use DB constraints and atomic transitions.

### Other security gaps before real data

- Encrypt database + backups at rest, properly manage secrets via vault and TLS; current SQLite files are unencrypted.
- Add per-organization row-level authorization; schema/migration versioning via Alembic, validated retention and data-subject actions.
- Add rate limits, audit read filtering, CSP, security headers, proper input sanitization/encoding for new UI, message abuse/attachment scanning.
- Implement pairing-scoped doctor-to-doctor chat **server-side**; v0.6 UX mock has peer messaging only in client state.
- Production web/video requires authenticated short-lived call tokens, clinician licensure and identity checks, safety notices, security threat modeling, consent and lawful purpose; no media recordings by default.
- AI adapter must be disabled by default, use synthetic-only test prompts; never send PHI to an external model without an approved vendor/data processing agreement and an explicit clinical review loop. Summaries must include provenance + disclaimer + user approval.
- No real patients, diagnoses, medical advice or protected health data in this prototype.

## Extensibility

API modifications belong in `backend/cc_api/extension_routes.py` and model definitions in `extension_models.py` (temporary demo structure). Real next step: split blueprints (`auth`, `previsit`, `messaging`, `invites`, `care_team`, `research`, `ai`) and issue Alembic revisions; maintain OpenAPI and mocked error fixtures. Frontend: move v0.6 route rendering into small page/controller modules; share tokens/themes/components; replace state mutations with transport adapters (`mock` vs `real`). Allow clinician-controlled field order and visible columns using user preferences, but **never** allow UI settings to elevate server-side field access.

## Current limits

Do not describe all 86 inventory routes as implemented. The UX mock is interactive but persists only within its JS state, while API Lab operates against persisted SQLite demo records. No real authentication, licensed telemedicine, production clinic PII, validated instrument scoring, real AI summary, live video, or real multi-clinic provisioning. Backend was syntax-checked locally; full pytest could not be executed in authoring environment because Flask was unavailable. See `docs/TEST_REPORT.md`.
