# Clinical Compass — ограничение расхода Codex Plus / subagent protocol

**Цель:** завершить работающий релиз для жюри, расходуя доступные запросы рационально. Точные лимиты подписки Plus и способ тарификации субагентов зависят от текущих условий продукта; проект **не предполагает определённой квоты** и **не обещает её экономию в процентах**. План ограничивает лишние запуски и сохраняет рабочее состояние для продолжения при достижении лимита.

## 1. Режим по умолчанию

1. **Один основной агент-координатор** владеет репозиторием, приоритетами, архитектурными решениями, сборкой, финальными тестами и отчётами. До делегирования он проверяет, можно ли решить задачу за счёт `rg`, `pytest`, имеющегося кода/скриптов и точечного изменения.
2. **Не запускать субагентов ради формальной многоролевой дискуссии**, повторного аудита или нескольких альтернатив одного решения. Один вызов допустим, только если работа независима, имеет измеримый конечный результат и её можно объединить без конфликта правок.
3. **Жёсткий стартовый бюджет:** не более **2 одновременно активных** субагентов; не более **4 отдельных делегирований за весь проект** без явного разрешения пользователя. Можно выполнить 0–4; это потолок, а не цель. Не создавайте вложенных субагентов и не делегируйте из субагента.
4. Если механизм субагентов недоступен в выбранной сессии Codex, **основной агент выполняет работу последовательно** по тем же пакетам. Не тратьте попытки на поиск скрытых агентов, переключение тарифов или неподдерживаемые параметры.
5. **До первого делегирования** зафиксировать исходную точку: git revision / SHA256 исходного архива, краткий каталог модулей, текущий результат smoke, приоритетные P0/P1 проблемы. Пересылать субагенту только краткий task packet и релевантные пути; не переписывать весь 40-страничный промпт в каждый вызов.

## 2. Кого делегировать и когда

| Очерёдность | Узкая задача | Когда оправдано | Выход | Ожидаемый владелец |
|---|---|---|---|---|
| A (Phase 0) | **Assessments + сохранение**: PHQ/GAD, guest→login/register, история, ACL | Если основной агент параллельно проверяет путь врача | Минимальный patch + регрессионный тест + PASS/FAIL | Backend/patient flows |
| B (Phase 0) | **Клинический каталог**: все 77 карточек, source-field coverage, pagination | Если устранение ошибок опросников отделено по файлам | Точечный patch + матрица покрытия | Catalog/backend/frontend detail |
| C (Phase 0/2) | **Ролевые UI пути**: доктор/исследователь/админ, 404/422/dead ends | Только если A/B уже зафиксированы и есть независимый набор файлов | Перечень blocker→fix→test; без изменения схемы без согласования | Frontend QA |
| D (Phase 3) | **Docker и Ollama connectivity** | Только после принятия Phase 0 и минимального Phase 2 smoke | Dockerfile/Compose + работающий smoke или воспроизводимый blocker | DevOps |

Phase 1 измерения и Phase 2 финальный прогон **по умолчанию делает основной агент**, используя один переиспользуемый набор Playwright сценариев/CSV, а не новых субагентов. Если реально нужна иная специализация, координатор может заменить один из четырёх слотов, не увеличивая их числа.

## 3. Обязательный формат короткого задания (task packet)

```text
TASK-ID: A | B | C | D
PHASE / PRIORITY: 0/P0 etc.
GOAL: одно измеримое действие и критерий принятия
FILES ALLOWED: конкретные каталоги/файлы, без случайных правок смежных модулей
BASELINE: одно предложение и ссылка на существующий тест/лог
DEPENDENCIES: контракты API, секреты/данные не передавать
COMMANDS TO VERIFY: 1–3 целевых запуска, не весь pytest/npm/e2e набор
EXIT: список изменённых файлов, один точечный тест, PASS/FAIL/BLOCKED
REPORT: ≤ 600 слов, ссылки на изменённые файлы и логи; без пересказа репозитория
STOP CONDITIONS: невозможность воспроизведения, конфликт правок, риск ACL/PII — вернуть blocker координатору
```

### Ограничения при выполнении

- На одного субагента — **один bounded task** и один рабочий набор файлов; не поручать "сделай весь backend/frontend" или "проверь весь проект".
- В параллельном режиме — непересекающиеся файлы/папки. Миграции, `AGENTS.md`, главный промпт, `PACKAGE_MANIFEST.json`, общие серверные конфигурации и release ZIP — **только у координатора**; конфликтную архитектуру решает координатор.
- Субагент **не создаёт других агентов**, не скачивает модели/пакеты и не запускает долговременный сервер, крупные pytest/e2e, npm install, Docker image build или нагрузочный прогон без разрешения координатора.
- Только локальная синтетическая QA БД; не отправлять или сохранять логины, куки, ключи, персональные данные. Не ослаблять CSRF/RBAC/consent/license checks.
- Вывод краткий: что изменено, почему, команды и фактические результаты, один список unresolved. Не дублировать большие исходники или логи в ответе: сохранять отчёт в файл.

## 4. Экономная последовательность исполнения

1. **Phase 0 прежде всего:** автопроверка всех маршрутов скриптом, а дорогие браузерные сценарии — по репрезентативным пользовательским путям и для каждого критичного CTA. Приоритет: гостевые анкеты и сохранение, роли/ACL, врачебный AI, все поля препаратов. После точечного исправления — сначала 1–3 целевых теста, затем общая регрессия в конце фазы.
2. **Phase 1 измерения пакетно:** один подготовленный набор Playwright скриптов, machine-readable CSV/JSON; ограниченная нагрузка без многократной генерации Qwen. Не запускать независимые идентичные benchmarks субагентами.
3. **Phase 2 фиксация готового:** оставить короткий сценарий жюри, тестовые синтетические кейсы и резервный интерактивный пример; перед новой задачей проверить имеющиеся реализации.
4. **Phase 3 Docker после работающего native gate:** избежать параллельного переписывания Docker и backend API. При возникновении безопасного сетевого blocker остановиться и документировать, не делать произвольную доступность Ollama наружу.
5. Повторять полный тестовый набор **по одному разу на контрольной точке фазы** и перед release, вместо полного прогона после каждой мелкой правки; безопасность и критичные регрессии проверять сразу точечным тестом.

## 5. Контрольные точки и восстановление при лимите

**Сохранение без потери результатов между лимитами:** после каждого завершённого пользовательского E2E-сценария, проверки карточки или короткой партии HTTP-замеров сохранять строку с фактическим исходом и временем в `reports/phaseN/raw/`. Для фазы 1 не собирать все показатели в памяти с записью только в конце: закрывать/сбрасывать файлы после каждого ограниченного пакета и сохранять `run_id`. После каждых 5 сценариев либо 10 минут активной работы (что раньше) и перед длительными операциями обновлять `reports/phaseN/PROGRESS.md`, `.agent/CHECKPOINT.md`, `.agent/EXECPLAN_ACTIVE.md`. В PROGRESS указывать доступные сырые данные, реальные n и диапазоны, частичный статус, следующий тест и точные команды возобновления. Даже если лимит оборвёт сессию без финального сообщения, все уже завершённые замеры должны оставаться на диске. Тесты, не проведённые до остановки, имеют статус `NOT_RUN`, а не `PASS`.

После каждой фазы/законченного блока создать или обновить в репозитории:

- `.agent/EXECPLAN_ACTIVE.md` — текущий этап, завершённые gate, следующий конкретный шаг, список файлов/владельцев, git rev, **остаток делегирований из 4**;
- `.agent/CHECKPOINT.md` — команды точного возобновления, окружение, порт, путь **только к отдельному QA workspace**, доступность Ollama/Chromium/Docker, PASS/FAIL/BLOCKED и пути логов;
- `reports/phaseN/` — CSV/JSON, скрипты, краткая таблица исходов; не хранить секреты и полные дампы сессий.

Нельзя начинать каждый новый чат с повторного тотального исследования; **первым прочитать AGENTS.md, CHECKPOINT.md, EXECPLAN_ACTIVE.md**, только затем конкретные затронутые модули. При достижении квоты дать пользователю компактную инструкцию продолжения после восстановления доступа. Никогда не заявлять, что работа продолжится автономно или уже выполнена, если на самом деле остановилась.

## 6. Компактный отчёт координатора (не больше одной страницы)

```text
PHASE / GATES: Phase N, PASS x / FAIL y / BLOCKED z
CHANGES: 3–8 важных файлов/функций
REAL TESTS: команды, длительность, факт, путь к доказательствам
SUBAGENTS: использовано X/4; активных Y (не более 2)
TOP P0/P1: упорядоченный остаток и кто владелец
NEXT 3 ACTIONS: конкретные команды/правки, без повторного аудита
RELEASE VERDICT: READY / READY_WITH_DISCLOSED_LIMITATIONS / NOT_READY
```

**Приоритет всегда у рабочего прототипа.** Экономия расхода не оправдывает фальсификацию зелёных тестов, нарушение безопасности, отключение обязательного подтверждения врача или отказ от проверки реального Qwen и сохранения данных.
